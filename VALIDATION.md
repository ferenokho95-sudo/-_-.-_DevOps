## Chaos evidence

Для Kuma crash, MariaDB crash и MariaDB stop/start зафиксирован переход
health **1 → 0 → 1** с timestamps. Значения читаются через Grafana API proxy
из datasource, использованного сохранённым дашбордом. При crash дополнительно
проверено увеличение `RestartCount`; сценарии прошли без ручного восстановления.
После отдельного stop/start Docker может сбросить RestartCount — итоговый снимок
не является историей всех перезапусков, для этого служат логи сценариев.

В ходе разработки обнаружено, что `docker kill` на этом демоне считается
ручной остановкой: первый вариант теста обоснованно упал. Исправленный вариант
замораживает контейнер для наблюдения красного статуса, затем завершает его
процесс через host PID helper с проверкой принадлежности PID по cgroup. Именно
этот вариант успешно проверен для обоих сервисов.

## Границы подтверждения

- Обе зависимости хоста передаются явно: `--socket=/var/run/docker.sock`
  и `--credentials=file:.env`. Оба параметра обязательны для запуска команд.
- Метрики хоста относятся к Linux/WSL, а не ко всей Windows.
- Предупреждения cAdvisor о machine-id/файловой системе возможны на Desktop;
  per-container filesystem usage не подтверждён. CPU/RAM и доступность проверены.
- Galera + HAProxy не используются. Один Docker-хост,
  одна MariaDB и restart-policy не обеспечивают HA при потере хоста/диска.
- Это приёмка в существующем окружении с постоянными томами, не отдельный тест
  на пустом новом хосте. Начальный запуск приложения и создание томов также
  выполнялись в ходе настройки, но сценарии chaos проверяют текущий стенд.
- Логи перед экспортом проверены на отсутствие значений паролей; `.env` в ZIP нет.
